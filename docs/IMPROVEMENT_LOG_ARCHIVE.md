# 프로젝트 개선 기록 보관함

## 2026-10-11 — 저장 실패 대응과 리플레이 데이터 보호

### 이전 작업 확인

- 이번 회차 시작 시 `IMPROVEMENT_LOG.md`가 없어 새로 작성했다. 작업 트리는 깨끗했다.
- `CHANGELOG.md`와 최근 Git 이력을 확인했다. 최근 작업은 v0.16.2 설정 화면 분류, v0.16.3 단축키 화면 너비 수정, v0.16.4 전적·패치노트·결과 안내 정리였다. 화면 재설계와 중복되지 않는 데이터 손실 및 실패 안내 문제를 선택했다.

### 구현한 개선

1. **설정·덱 저장 실패를 성공으로 안내하던 문제 수정**
   - `SettingsScreen.gd`, `DeckScreen.gd`에서 `SaveData.save_data()`의 반환값을 확인한다.
   - 저장할 내용을 별도 사본에 구성하고, 디스크 저장이 성공한 뒤에만 현재 프로필에 적용한다. 실패하면 기존 설정·사용 덱·목표 진행을 유지하고 편집 화면에 오류와 재시도 안내를 표시한다.
   - 실패한 입력은 화면에 남아 다시 저장할 수 있다. 설정 취소 시에는 기존 오디오 설정으로 돌아간다.
2. **리플레이 파일 덮어쓰기와 메모 수정 중 손실 방지**
   - 기존 저장 이름은 초 단위라 같은 초에 같은 이름으로 저장하면 이전 파일을 덮어썼다. 시간에 따른 고유 접미사와 충돌 확인을 추가했다. 접미사를 이름 힌트보다 앞에 배치해 같은 초의 기록도 시간순으로 정렬한다.
   - 새 저장과 메모 수정은 `.tmp` 파일에 쓰고 오류를 확인한 뒤 기존 파일을 교체한다. 실패한 교체는 원본 파일을 유지하고 새 파일 저장 실패 시에는 기록 정리를 실행하지 않는다.
   - 로컬 리플레이 뷰어에서 메모 저장 실패를 사용자에게 알린다.
3. **잘못된 외부 리플레이가 화면·재생에 도달하는 경로 차단**
   - 버전, 재생 속도, 결과, 표시용 메타데이터, 덱 항목의 자료형을 확인한다. 소수·무한대·잘못된 객체를 정수나 문자열로 변환하기 전에 거부한다.
   - 명령, 강제 종료, 클립, 메모의 시간을 검사하고 기록의 끝을 넘는 위치를 거부한다. JSON에서 정수가 실수형으로 복원되는 정상적인 경우는 계속 허용한다.
   - 새 저장에서도 유효성을 확인한다. 정상 리플레이 형식 번호와 공유 접두사, 기존 파일 읽기 방식은 유지했다.
4. **단축키 편집의 저장 안내 보완**
   - 키 지정과 기본값 복원으로 저장된 키와 다른 설정이 되면 다른 설정 항목과 같은 ‘저장하지 않은 변경’ 표시를 띄운다.
   - 저장 오류 안내가 긴 경우 설정 하단에서 줄바꿈하도록 했다.

### 검증

- 새 테스트 파일이나 테스트 묶음은 추가하지 않고 기존 테스트에 재현 사례를 넣었다. 실제 임시 저장 경로를 디렉터리로 막아 파일 쓰기 실패를 유발하고, 원본 유지·오류 안내·입력 유지·재시도 성공을 확인했다.
- Godot 4.7.2 헤드리스에서 관련 GDScript 테스트 **12개 통과**:
  - 저장·공유: `replay_test.gd`, `replay_shelf_test.gd`
  - 편집 화면: `helper_settings_test.gd`, `key_bindings_test.gd`, `replay_notes_test.gd`, `replay_clip_test.gd`
  - 기존 기능: `daily_challenge_test.gd`, `weekly_challenge_test.gd`, `draft_mode_test.gd`, `practice_replay_test.gd`, `ui_flow_test.gd`, `replay_viewer_plus_test.gd`
- `suites_cover_all_tests_test.py` 통과, `git diff --check` 통과.
- 새 회귀 테스트의 타입 추론 오류 한 건을 명시적 `Dictionary` 선언으로 수정한 뒤 해당 테스트를 다시 실행했다. 저장 이름의 최종 정렬 보정 뒤에는 리플레이 저장 검증만 재실행했다.
- 각 실행의 `APPDATA`를 프로젝트 안 `.godot/validation-user/<테스트명>`으로 분리해 실제 사용자 저장 파일과 리플레이에 영향을 주지 않았다. Godot가 자동으로 바꾼 에셋 가져오기 메타데이터와 생성한 UID 파일은 원상복구했다.
- 헤드리스 UI 동작을 확인했으며 실제 기기에서 화면을 렌더링한 검증은 수행하지 않았다. 이 환경의 인증서 저장소 오류 메시지는 테스트 통과를 막지 않았다.

### 다음 개선 후보

1. **전투 결과·진행도 자동 저장 실패 안내와 재시도**: `ResultScreens.gd` 등의 자동 저장에서도 반환값을 무시한다. 결과를 중복 집계하지 않으면서 실패를 알리고 다시 저장할 수 있는 방법을 우선 검토한다.
2. **원격 리플레이의 메모 보관**: 코드로 연 리플레이에는 파일 경로가 없어 메모가 디스크에 저장되지 않는다(`ReplayScreens._play_replay_data`). 로컬 보관 기능이나 화면 안내가 필요하다. 로컬 파일의 저장 실패 시 메모는 현재 뷰어 안에만 남으므로, 미저장 상태 및 재시도도 함께 검토한다.
3. **매우 긴 전투의 리플레이 한계 안내**: 전투에는 시간 제한이 없지만 리플레이는 `MAX_TICKS`와 `MAX_COMMANDS` 상한이 있다. 상한 도달 시 조용히 잘리는 명령과 저장 불가 상황을 먼저 확인하고, 기록 가능 범위와 안내를 일치시킨다.

Git 커밋·푸시는 수행하지 않았다. 출시 버전과 전투 규칙은 변경하지 않았다.

## 2026-10-11 — 전적 저장 재시도와 공유 리플레이 메모 보관

### 이전 작업 확인

- 앞선 회차의 설정·덱 저장 실패 처리, 리플레이 원자적 저장과 외부 데이터 검증을 확인했다. 기존 기능을 다시 구현하지 않고, 기록에 남은 자동 저장 실패와 원격 리플레이 메모 손실 문제를 이어서 해결했다.
- 작업 시작 시 Git 작업 트리는 깨끗했다. `SaveData.save_data()` 호출과 결과·메뉴·리플레이 화면 흐름을 함께 확인했다.

### 구현한 개선

1. **전적·진행도 자동 저장 실패 안내와 안전한 재시도**
   - `Main._save_profile()`로 자동 저장을 모으고 실패 상태를 기억한다. 결과, 튜토리얼, 시작 목표, 닉네임·선택 덱, 전체 화면 설정, 결과 공유 설정 등에 같은 처리를 적용했다.
   - 실패하면 메모리의 새 전적·점수·업적을 유지하면서 저장 공간·파일 권한 확인 안내와 ‘저장 재시도’를 표시한다. 결과 화면을 닫거나 메뉴를 이동해도 안내가 유지된다.
   - 재시도는 현재 프로필을 디스크에 쓰는 작업만 한다. 전투 결과 집계와 업적 지급을 다시 실행하지 않는다. 기존 `result_recorded` 보호도 유지했다.
   - 설정·덱 편집의 성공적인 저장 역시 미저장 상태를 해제한다. 데이터 초기화 후에는 이전 저장 경고를 제거한다.
   - 미저장 진행도가 있을 때 자동 업데이트의 설치·재시작을 보류한다. 결과 저장을 먼저 시도한 후 업데이트 가능 상태를 결정하도록 순서를 바꿨다.
   - AI 결과의 기본 안내는 ‘전적에 반영’으로 표현해 디스크 저장 실패 때 성공을 단정하지 않도록 했다.

2. **공유 리플레이 로컬 보관과 메모 저장 복구**
   - 코드·최근 온라인 전투로 연 리플레이에 ‘로컬 보관’ 버튼과 보관 상태를 추가했다. 메모 없이도 저장할 수 있으며 첫 메모를 남기면 자동으로 로컬 사본을 만든다.
   - 이후 메모 추가·삭제는 같은 파일을 갱신한다. 매번 새 사본이 만들어지지 않는다.
   - 로컬·원격 리플레이 모두 메모 저장 실패 상태와 재시도 버튼을 유지한다. 재시도만으로 뷰어에 남은 메모를 저장할 수 있다.
   - 미저장 메모가 있는 상태로 나가면 돌아가서 재시도하거나 변경을 버리고 나가도록 안내한다. ‘여기서 해보기’ 전환과 자동 업데이트도 미저장 메모가 유실되지 않도록 보류한다.
   - 되감기 실험에 전달하는 데이터는 처음 열었던 사본 대신 현재 뷰어의 리플레이를 사용해 최신 메모를 포함한다. README에 공유 리플레이 보관 방법을 추가했다.

### 검증

- 새 테스트 파일·묶음은 추가하지 않았다. 기존 온라인 결과·일일 도전·리플레이 메모 테스트에 실제 파일 쓰기 실패와 재시도 사례를 보완했다.
- 저장 파일의 `.tmp` 경로를 디렉터리로 막아 기존 파일 유지, 새 결과의 메모리 유지, 화면 이동 후 재시도, 결과 중복 집계 방지, 일일 점수·업적 보관을 확인했다.
- 공유 리플레이 저장 폴더 자리에 파일을 두어 첫 메모 저장 실패를 유발했다. 복구 후 재시도, 같은 사본의 갱신, 다시 열었을 때 메모 복원, 메모 없이 직접 보관하는 동작을 확인했다.
- Godot 4.7.2 헤드리스에서 관련 테스트 **11개 통과**: `online_result_ui_test.gd`, `daily_challenge_test.gd`, `replay_notes_test.gd`, `ui_flow_test.gd`, `weekly_challenge_test.gd`, `practice_campaign_test.gd`, `replay_viewer_test.gd`, `replay_clip_test.gd`, `helper_settings_test.gd`, `data_reset_test.gd`, `new_features_test.gd`.
- 일일 도전의 저장 검증은 JSON 왕복 전후 전체 실수 데이터의 동등성 대신 전적·점수·업적과 메모리 결과 불변을 확인하도록 보완했다. 추가 메모 테스트에서 잘못 호출한 Main 진입점을 실제 `ReplayScreens` 진입점으로 수정했다. 이 실행은 제한 시간 종료 후 해당 테스트만 재실행했다.
- 리플레이 뷰어의 기존 삭제 검증은 최신순 목록의 첫 버튼을 누른 뒤 더 오래된 원본 파일이 삭제됐는지 확인하는 가정을 갖고 있었다. 실제 첫 항목의 경로로 검증 대상을 수정하고 해당 테스트만 재실행했다.
- 테스트마다 `APPDATA`를 `.godot/validation-user/iteration2/<테스트명>`으로 분리했다. 실제 사용자 프로필·리플레이를 사용하지 않았다. 테스트가 만든 파일은 무시되는 `.godot` 아래에만 있다.
- `git diff --check` 통과. 변경된 출시 버전·전투 규칙·새 의존성은 없다. 실제 화면 렌더링과 기기 터치 검증은 하지 않았으며, 환경의 인증서 저장소 오류와 일부 기존 종료 시 객체 누수 경고는 남아 있다.

### 다음 개선 후보

1. **전투 종료 시 리플레이 저장 실패 복구**: `ResultScreens.gd`는 리플레이 저장 결과가 빈 경로여도 기록기를 폐기한다. 프로필 저장과 별개로 완성된 리플레이를 보관하고 저장 실패를 안내·재시도하는 흐름을 검토한다.
2. **데이터 전체 초기화의 부분 실패 안내**: `DataReset.gd`는 파일 삭제 실패를 충분히 알리지 않고 기본 프로필로 돌아간다. 삭제되지 않은 파일과 다시 시작할 때 옛 데이터가 나타날 가능성을 확인한다.
3. **매우 긴 전투의 리플레이 한계 처리**: 이전 회차 후보인 `MAX_TICKS`·`MAX_COMMANDS` 상한과 실제 기록 가능 범위의 일치, 상한 도달 안내를 이어서 검토한다.

## 2026-10-11 — 전투 리플레이 복구와 데이터 초기화 실패 처리

### 이전 작업 확인

- 앞선 두 회차의 프로필 저장 재시도, 공유 리플레이 보관·메모 복구를 확인했다. 작업 시작 시 Git 작업 트리는 깨끗했다.
- 이전 후보였던 전투 종료 시 리플레이 저장 실패, 전체 초기화의 부분 실패, 매우 긴 전투의 기록 한도를 조사했다. 기존 편집 화면이나 프로필 재시도를 다시 구현하지 않고 남아 있던 손실 경로를 해결했다.

### 구현한 개선

1. **전투 종료 시 리플레이 저장 실패 복구**
   - 완성된 리플레이를 전투 모델·기록기와 별개로 보관한다. 저장에 실패해도 메뉴 이동과 다음 전투 시작으로 기록이 사라지지 않는다.
   - 화면 상단에 미저장 리플레이 개수와 ‘저장 재시도’를 표시한다. 여러 전투가 실패해도 각각 보관하며, 성공한 항목만 대기 목록에서 제거해 중복 저장을 막는다.
   - 재시도는 파일 저장만 수행하므로 전적·업적을 다시 집계하지 않는다. 프로필 저장 실패와 동시에 발생하면 두 안내와 버튼을 따로 표시한다.
   - 클라이언트의 업데이트 가능 조건을 모아 미저장 리플레이가 있으면 프로필·메모 저장 성공이나 메뉴 이동으로 자동 업데이트가 재개되지 않도록 했다. 결과 집계와 프로필 쓰기가 끝나기 전에도 업데이트를 재개하지 않는다.

2. **전체 초기화의 실제 삭제 결과와 안전한 재시도**
   - 파일·리플레이 삭제 결과를 확인하고 실제 삭제한 개수와 실패 경로를 반환한다. 하위 폴더의 리플레이도 실제 삭제 개수에 포함한다.

   - 완성된 기록을 전투 모델과 별개로 보관하고 원본 아카이브·공개 공유 보관함의 성공 여부를 각각 기억한다. 방 삭제·전투 정리 뒤에도 실패한 목적지를 다시 저장할 수 있다.
   - 30초 간격으로 실패한 목적지만 재시도한다. 이미 성공한 아카이브·공유 항목을 중복 생성하지 않고 전투 결과 통계를 다시 집계하지 않는다. 최초 실패와 복구를 서버 로그에 남긴다.
   - 공유 텍스트는 한 번 생성해 재시도에 사용한다. 공유 크기 상한을 넘는 기록은 원본 아카이브는 저장하되 공유 불가 이유를 기록하고 무한 재시도·업데이트 영구 보류를 피한다.

2. **공유 코드의 디스크 저장 확인과 안전한 보관함 갱신**
   - 디스크 보관함은 파일 저장 성공 후에만 새 코드를 반환하고 메모리 목록·인덱스를 갱신한다. 실패한 비공개→공개 전환은 기존 파일·공개 상태를 유지하며 같은 코드로 재시도할 수 있다.
   - 공백을 정규화한 텍스트의 SHA-256으로 중복을 확인한다. 종전에는 공백을 포함한 입력으로 해시를 만들고 정규화한 내용을 저장해 재시작 전후 중복 처리에 차이가 있었으며, 짧은 정수 해시 충돌에도 영향을 받았다.
   - 새 코드 생성 시 디스크에 남아 있는 파일·디렉터리도 충돌 대상으로 확인해 읽기에서 제외된 원본을 덮어쓰지 않는다.
   - 시작 시 공유 텍스트와 공개 여부를 검증하고 표시용 요약을 실제 리플레이에서 다시 만든다. 잘못된 파일을 목록·재생 요청으로 전달하지 않는다. 기존 보관함 파일도 계속 읽는다.
   - 생성 시각을 저장해 같은 초의 기록과 공개 전환 뒤에도 새 기록의 순서를 유지한다. 시작 시에도 보관 상한을 적용한다.
   - 오래된 파일 삭제 실패는 항목을 잊지 않고 로그·주기적 재시도로 처리한다. 상한을 넘은 상태에서는 추가 업로드를 거부해 계속 늘어나지 않도록 한다.
   - 클라이언트의 코드 발급 실패 버튼은 ‘재시도’로 표시하고 다시 누르기·텍스트 복사 대안을 안내한다.

3. **통계·순위표 재시도와 서버 업데이트 연결**
   - 통계·도전 순위표도 서버가 유휴 상태일 때 주기적으로 저장한다. 업데이트 대기 진입 시에는 즉시 저장을 시도한다.
   - `server-status.json`에 `pending_saves`를 기록하고, 전투 기록·통계·순위표의 미저장 데이터가 있으면 서버 자동 업데이트와 재시작을 보류한다. 기존 Linux 업데이트 스크립트의 `safe_to_update` 확인을 그대로 사용한다.
   - 공통 JSON 저장에서 실제 쓰기·flush 오류를 확인하고 성공 후 원본을 교체한다. 저장 폴더를 다시 만들 수 있어 폴더 장애 복구 후 재시도가 가능하다. 서버 상태 파일도 기존 파일을 먼저 삭제하지 않고 같은 방식으로 갱신한다.

4. **기본 서버 실행에서도 공유 기록 유지**
   - `CATWAR_STATE_DIR`이 없으면 `user://server_state`에 공유 코드·통계·순위표를 저장한다. 종전 기본 실행은 이 데이터를 메모리에만 보관했다. 지정된 운영 서버 상태 경로는 계속 사용하며 전투 원본 경로도 유지한다.
   - `server/README.md`에 기본 경로, 저장 실패 로그·재시도, 업데이트 보류, 보관 상한을 기록했다.

### 검증

- 새 테스트 파일·묶음은 추가하지 않았다. 기존 리플레이·보관함·통계·네트워크 테스트에 실제 경로 장애와 복구 사례를 보완했다.
- 보관 폴더 자리에 파일을 두거나 임시 저장 경로를 디렉터리로 막아 실패를 재현했다. 원본 유지, 실패 코드 반환, 공개 전환 복구, 전투 정리 뒤 재시도, 아카이브·공유·통계 중복 방지와 복구된 리플레이의 재생 결과 일치를 확인했다.

## 2026-10-11 — 통계·순위표 손상 데이터 보호와 동점 재도전 반영

### 이전 작업 확인

- 이전 다섯 회차의 클라이언트 원본 보호·저장 재시도, 서버 기록 보관·공유 코드 저장 복구를 확인했다. 작업 시작 시 Git 작업 트리는 깨끗했다.
- 이전 후보인 `ServerStats._sanitize_section()`과 `ServerDailyBoard.configure()`의 내부 검증 부족을 조사했다. 실제 실행에서 딕셔너리를 숫자로 변환할 때의 오류와 숫자 형태의 순위 항목에서 닉네임을 조회할 때의 오류를 재현했다.
- 순위표가 동점일 때 완료 시간으로 정렬하지만, 더 빠른 동점 재도전을 서버·로컬 기록·오프라인 대기열 모두에서 버리는 문제를 확인했다. 클라이언트 통계 캐시는 중첩 필드를 검증하지 않으며 덱 조회가 누적되면 자체 읽기 한도를 초과한다는 점도 확인했다.

### 구현한 개선

1. **서버 통계의 항목별 검증**
   - 숫자로 바꾸기 전에 자료형, 유한성, 정수 여부, 음수·범위를 확인한다. JSON에서 정수가 실수 형태로 복원되는 정상 경우는 계속 허용한다.
   - 정상 덱·유닛·구조물 이름과 승리·무승부 합계를 검증한다. 전체 경기 수를 초과하는 개별 집계도 제외한다. 잘못된 항목 때문에 정상 항목의 로드·조회·새 결과 집계가 중단되지 않는다.
   - 기존 파일 형식과 온라인/보고 집계 구분을 유지한다. 읽기 자체는 원본 파일을 다시 쓰지 않는다.

2. **서버 순위표와 클라이언트 표시 데이터 보호**
   - 저장된 순위표의 참가 ID, 닉네임, 점수, 완료 시간을 확인하고 정상 항목만 읽는다. 날짜는 실제 달력 날짜여야 하며 주간 키는 월요일이어야 한다. 일별 참가 상한도 읽기에서 적용한다.
   - 클라이언트는 서버 응답·캐시의 덱 행, 유닛·구조물 집계, 신뢰도 수치와 순위표의 시간·순위·내 점수까지 확인한다. 잘못된 응답은 현재 정상 통계를 교체하지 않으며 잘못된 디스크 캐시는 표시 전에 제외한다.
   - 정상 저장 형식, 실제 서버 응답과 화면 구성을 유지한다. 서버 파일에서 제외된 항목은 이후 정상 제출로 다시 기록할 수 있다.

3. **일일·주간 도전의 동점 최고 기록 개선**
   - 점수 우선, 동점이면 짧은 완료 시간이라는 비교를 공통화했다. 로컬 최고 기록·오프라인 전송 대기열·서버 순위표가 모두 더 빠른 동점 기록을 반영한다.
   - 더 빠른 동점은 최고 기록 갱신으로 처리하고 클리어 개수를 중복 증가시키지 않는다. 더 느린 동점은 기존 시간을 유지하며 서버의 닉네임 갱신 동작도 유지한다.
   - README와 서버 문서에 정렬·재도전 처리와 손상 항목 제외 동작을 기록했다. 점수 계산식과 전투 규칙은 변경하지 않았다.

4. **덱 조회 캐시의 지속성 보완**
   - 최신 조회 덱부터 유지하면서 누적 조회를 기존 12개 한도로 제한한다. 12종을 넘게 조회해도 재시작 뒤 캐시를 읽을 수 있다.
   - 캐시 저장 시 입력 사본을 사용하고 서버의 경기 수가 감소하면 이전 집계의 조회 기록을 비운다. 초기화된 서버에 과거 기록이 남는 문제를 피한다.

### 구현한 개선

1. **자동 정리의 원본 보존과 실제 결과 확인**

## 2026-10-11 — 익명 결과·도전 점수의 저장 확인과 중복 없는 재전송

### 이전 작업 확인

- 앞선 일곱 회차의 저장 보호·서버 복구·통계 검증·전투 수락 제어를 확인했다. 작업 시작 시 Git 작업 트리는 깨끗했다.
- 첫 후보인 `MetaStats.flush()`를 조사했다. 연결 상태만 확인하고 RPC 전송 직후 결과·도전 점수 대기열을 비우지만 서버는 요청 제한·결과 개수 제한·디스크 실패로 처리를 완료하지 않을 수 있었다. 기존 읽기·저장 재시도를 다시 구현하지 않고, 클라이언트 대기열과 서버 처리 완료 사이의 확인 경로를 보완했다.

### 구현한 개선

1. **기기에 보관한 대기열을 서버 저장 확인 후 삭제**
   - 전송만으로 결과·점수 대기열을 지우지 않는다. 서버의 저장 확인 응답이 해당 설치 ID·결과 순번 또는 날짜·점수·완료 시간과 일치할 때만 제거하고 변경된 프로필을 저장한다.
   - 결과를 공유하기 전에 진행도와 대기열·설치 ID를 먼저 저장한다. 프로필 저장이 실패한 동안에는 자동·연결 완료·지연된 접속 콜백 모두 결과 전송을 보류한다.
   - 기존 구형 프로필의 대기 결과에 순번을 부여하며, JSON 저장·로드 시 순번과 다음 번호를 유지한다. 기존 진행도·저장 버전·공유 기본 꺼짐 설정은 유지했다.

2. **익명 통계의 영속적인 중복 방지**
   - 설치별 마지막 결과 순번을 규칙 버전별 통계 카운터와 같은 파일에 원자적으로 저장한다. 저장 실패 때 확인 응답을 보내지 않으며, 같은 결과의 재시도는 이미 반영한 카운터를 증가시키지 않고 저장을 다시 시도한다.
   - 확인 응답 유실·재접속·서버 재시작·기기에 남은 오래된 대기열에서도 같은 규칙 버전의 결과는 한 번만 집계한다. 순번이 앞서 처리되는 일을 막기 위해 대기 결과를 하나씩 순서대로 전송한다.
   - 기존 요청 속도와 연결당 결과 개수 제한을 유지한다. 재시도는 새 결과 개수로 세지 않는다. 설치별 순번은 최대 100,000개 설치까지 보관하고, 상한에서는 기존 중복 방지 기록을 버리는 대신 새 설치의 전송 확인을 보류한다. 온라인 통계와 기존 설치·도전 점수는 계속 처리한다.
   - 저장하는 추가 정보는 익명 설치 ID와 순번뿐이다. 개별 덱 이력·닉네임·IP를 결과 확인 기록에 추가하지 않는다. 기존 통계 파일은 추가 필드 없이도 계속 읽는다.

3. **도전 점수 확인과 자동 재시도**
   - 일일·주간 점수는 순위표 파일 저장이 성공한 뒤에만 확인 응답을 보낸다. 순위표 조회 응답과 전송 대기열 삭제를 분리했다.
   - 먼저 보낸 점수의 확인이 늦게 도착해도 그 사이에 얻은 더 높은 점수·빠른 동점 기록을 지우지 않는다.

## 2026-10-11 — 통계 버전 분리와 장기 연결 전송 복구, 도전 화면 접근성

### 이전 작업 확인

### 구현한 개선

1. **실제 콘텐츠 버전별 통계 저장·전송**
   - 통계 버전 식별자가 생성된 빌드 정보의 `version`을 읽도록 수정했다. 서버는 기본 구성에서 `stats_<콘텐츠 버전>.json`을 사용한다.

   - 현재 버전 결과 중 가장 오래된 것부터 하나씩 보내고 해당 결과의 확인만 삭제한다. 이전·미상 버전 결과는 기존 최근 20개 대기열 정책 안에서 남기며 현재 결과의 전송을 막지 않는다. 설치 ID와 전체 결과 순번은 유지한다.

3. **결과 공유 상태 표시**

4. **긴 도전 안내에서도 시작·돌아가기 버튼 유지**
