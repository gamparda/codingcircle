# 전체 플레이어 통계·순위표 설계 (초안)

상태: 구현됨(미출시). 결정: 클라이언트가 보고한 결과는 일단 그대로 신뢰하고, 이상치가 생기면 검증(리플레이 재계산)을 추가한다. 이를 위해 온라인(서버 판정)과 보고(클라이언트 신뢰) 집계를 분리해 보관하고 순위표에 `verifier` 훅을 둔다. 아래 3·5절의 재계산 검증과 AI 결과 제외는 이번 구현에서 하지 않았다.

## 1. 전제 (현재 구조에서 확인한 사실)

- 서버는 같은 Godot 코드로 돌아가는 권위 서버이고 UDP(ENet)만 쓴다. HTTP·DB·계정이 없다.
- 온라인 전투는 서버가 시뮬레이션하므로 **결과(승패·덱·시간)는 클라이언트가 조작할 수 없다.** 서버는 이미 매치 종료 시 `ServerReplays.settle`에서 리플레이를 만든다.
- 사용자 식별은 닉네임과 재접속 토큰뿐이다. 닉네임은 중복·위장이 가능하다.
- 전투는 결정적이고 리플레이에 결과 해시가 있어 **서버가 제출된 리플레이를 다시 계산해 검증할 수 있다.**
- 서버·클라이언트는 항상 함께 업데이트된다(프로토콜 변경이 자유롭다).

## 2. 범위: 세 단계로 나눈다

| 단계 | 내용 | 클라이언트 업로드 | 위험 |
|---|---|---|---|
| A | 온라인 매치에서 모은 **전체 덱 통계** | 없음 | 낮음 |
| B | **일일 도전 순위표** | 리플레이 1건 제출 | 중간 (검증 필요) |
| C | 전체 통계로 덱 분석·시뮬레이터 보강 | 없음 (읽기만) | 낮음 |

A → C → B 순서를 권장한다. A·C는 업로드가 없어 개인정보 부담이 거의 없다.

## 3. 단계 A: 서버 집계

### 집계 시점과 방식
`ServerReplays.settle`과 같은 지점(매치 종료)에서 `ServerStats.record(match)`를 호출한다. 리플레이 원본은 쌓지 않고 **카운터만** 갱신한다.

기록하는 값(매치 1건당):
- 규칙 버전 키 `ruleset` (콘텐츠 버전 + 데이터 해시)
- 양쪽 병력 덱(정렬한 3종 조합), 구조물 덱(정렬한 3종 조합), 승패/무승부, 경기 시간 구간(구간화)
- 덱 조합별 `games`, `wins`, `draws`; 병력·구조물 개별 `picked`, `won_with`

기록하지 않는 값: 닉네임, IP, 재접속 토큰, 방 코드, 명령 시퀀스.

### 저장
- `CATWAR_STATE_DIR/stats/<ruleset>.json` 하나. 최상위 키는 `ruleset`, 값은 카운터 사전.
- 임시 파일에 쓰고 rename하는 원자적 저장, 매치 N건마다 또는 60초마다 flush. 손상 시 직전 백업으로 복구.
- 규칙 버전이 바뀌면 새 파일로 시작한다(밸런스가 바뀐 뒤의 승률을 옛 숫자와 섞지 않는다).

### 신뢰할 수 있는 통계로 만들기
- 표본이 적은 항목은 숨긴다(최소 표본 `MIN_SAMPLES`, 데이터 상수로 정의). 코드에 숫자를 박지 않는다.
- 순위는 단순 승률이 아니라 **윌슨 하한** 같은 신뢰구간 하한으로 정렬한다.
- 미러 매치(같은 덱끼리)와 한쪽이 연결 끊김/항복한 매치는 별도 표시하거나 제외한다.
- 화면에 "표본 N판, 온라인 대전 기준"을 항상 같이 보여 준다. 선택 편향(고수가 쓰는 덱이 높게 나옴)이 있다는 점을 안내문에 적는다.

### 프로토콜
- 요청: `request_meta_stats(ruleset)` 하나. 응답: 상위 덱 조합, 병력·구조물별 선택률/승률, 총 표본 수.
- 서버는 응답을 일정 주기로 **캐시한 스냅샷**으로 만들어 두고 요청마다 계산하지 않는다.
- 기존 `can_process_request` 속도 제한을 그대로 적용하고, 응답 크기에 상한을 둔다.

## 4. 단계 C: 클라이언트 반영

- `DeckAnalysis` 화면에 "내 기록 / 전체" 두 열을 나란히 보여 준다. 서버 연결이 없으면 전체 열은 숨긴다.
- `DeckSimulator`의 팁에 "현재 전체 플레이어에서 이 덱의 승률 순위" 한 줄을 추가한다. 시뮬레이션 결과(대 AI)와 실전 승률(대 사람)은 의미가 다르므로 **합치지 않고 따로 표기**한다.
- 받은 스냅샷은 `ruleset`과 함께 로컬에 캐시하고, 규칙 버전이 다르면 폐기한다.

## 5. 단계 B: 일일 도전 순위표

### 아이디 문제
계정이 없어서 닉네임으로는 중복 제출·사칭을 막을 수 없다. 기기 로컬에서 만든 **랜덤 설치 ID**(UUID)를 쓴다.
- 장점: 로그인 없이 "1인 1일 1기록"을 대략 보장한다.
- 한계: 앱을 지우거나 ID를 바꾸면 여러 기록을 낼 수 있다. 가벼운 순위표 용도에서는 허용하고, 이 한계를 문서·화면에 밝힌다.

### 제출과 검증
1. 클라이언트가 일일 도전 결과 리플레이(압축 텍스트)와 설치 ID, 닉네임을 제출한다.
2. 서버가 크기·형식을 검사하고 `BattleReplay.valid`를 통과시킨다.
3. **오늘의 도전과 일치하는지 확인한다.** 서버가 `DailyChallenge.for_date(date)`로 직접 만든 설정과 리플레이의 `setup`이 정확히 같아야 한다. 날짜는 서버 UTC 기준 당일(자정 직후 유예 포함)만 받는다.
4. `BattleReplay.verify`로 재계산해 결과 해시가 맞는지 확인한다. 점수는 **서버가 재계산한 결과로 `DailyChallenge.score`를 호출해 직접 산출**한다. 클라이언트가 보낸 점수는 쓰지 않는다.
5. 설치 ID별 당일 최고 점수만 보관한다.

### 비용 통제
- 재계산은 서버 CPU를 쓰므로 **검증 큐**를 두고 동시 1건, 설치 ID/IP별 제출 간격 제한, 리플레이 크기 상한을 둔다.
- 검증은 전투 틱 루프를 한 번 돌리는 정도이며, 진행 중인 매치 시뮬레이션을 방해하지 않도록 프레임당 예산(`step(budget)` 방식)으로 나눠 처리한다.

### 조회
- `request_daily_board(date)` → 상위 일정 개수의 (닉네임, 점수, 시간) + 내 순위. 닉네임은 표시 전에 기존 닉네임 정제 규칙을 거친다.
- 보관: 최근 일정 기간의 날짜만 유지하고 그 이전은 삭제한다.

## 6. 개인정보·옵트인

- 단계 A는 서버가 이미 보는 정보만 집계하며 개인 식별 정보를 저장하지 않는다. 그래도 설정 화면과 README에 "온라인 대전 결과는 익명 통계로 집계된다"고 알린다.
- 단계 B는 **옵트인**(기본 꺼짐)이다. 켜면 닉네임이 순위표에 공개된다는 점을 확인 문구로 보여 준다. 끄거나 삭제를 요청하면 설치 ID에 연결된 기록을 지운다.
- 로그에 IP와 설치 ID를 함께 남기지 않는다.

## 7. 구현 계획

| 순서 | 작업 | 주요 파일 |
|---|---|---|
| 1 | `ServerStats`: 카운터, 저장, 규칙 버전 키, 스냅샷 | `scripts/ServerStats.gd`, `ServerBattle.gd` |
| 2 | 프로토콜: `request_meta_stats`, 속도 제한, 크기 상한 | `NetworkController.gd` |
| 3 | 클라이언트 캐시 + DeckAnalysis "전체" 열 | `DeckAnalysis.gd`, `ReplayScreens.gd` |
| 4 | 시뮬레이터 팁에 전체 순위 한 줄 | `DeckSimulator.gd` |
| 5 | `ServerDailyBoard`: 검증 큐, 저장, 조회 | `scripts/ServerDailyBoard.gd` |
| 6 | 순위표 화면과 옵트인 설정 | `PracticeUI`, 설정 화면 |
| 7 | 문서·패치노트·릴리스 | README, CHANGELOG |

## 8. 테스트 계획

- 집계: 가짜 매치 N건 → 카운터와 윌슨 정렬 확인, 표본 부족 항목 숨김, 미러/항복 제외.
- 영속성: 재시작 후 복원, 손상 파일 복구, 규칙 버전 변경 시 분리.
- 프로토콜: 속도 제한, 응답 크기 상한, 버전 불일치 거부.
- 순위표 검증: 정상 제출 통과 / 명령 변조 / 결과 해시 변조 / 다른 날짜 설정 / 오늘이 아닌 날짜 / 과대 크기 / 중복 제출 / 설치 ID당 최고 점수 유지.
- UI: 서버 없음 상태에서 "전체" 열이 숨겨지는지, 옵트인 흐름.
- 정책 테스트: 새 테스트 파일을 `tests/suites.json`에 등록, README에 밸런스 수치 금지.

## 9. 결정이 필요한 항목

1. **단계 B(순위표)까지 할지**, 아니면 A·C(전체 통계)만 먼저 할지. 권장: A·C 먼저.
2. 전체 통계의 대상을 **온라인 대전만**으로 할지. 권장: 온라인만(서버가 결과를 보증함). 클라이언트가 보고하는 AI 대전 결과는 조작 가능해서 제외한다.
3. 순위표를 도입한다면 **설치 ID 방식의 한계(1인 다중 기록 가능)를 허용**할지. 허용하지 않으려면 계정 시스템이 필요하며, 이는 별도 대형 작업이다.
